# Лабораторна робота №2: Дослідження зв'язку між мовою C та Assembly

## 1. Мета лабораторної роботи
У попередній лабораторній роботі ми досліджували, як дані представлені в пам'яті комп'ютера. Тепер переходимо від даних до інструкцій.

Головне питання лабораторної роботи: **Що насправді виконує процесор замість написаного нами C-коду?**

Під час роботи ми простежимо шлях:
C source code ➡️ Compiler ➡️ Assembly ➡️ Assembler ➡️ Machine code ➡️ CPU

**Мета** — не навчитися програмувати на Assembly, а навчитися читати простий Assembly та встановлювати зв'язок між конструкціями C і машинними інструкціями.

---

## 2. Результати навчання
Після виконання лабораторної роботи студент повинен уміти:
* Отримувати Assembly-код із програми C;
* Пояснювати різницю між C, Assembly та machine code;
* Знаходити функції у дизасембльованій програмі;
* Розпізнавати базові інструкції `mov`, `add`, `sub`, `cmp`, `jmp`, `call`, `ret`;
* Знаходити в Assembly арифметичні операції;
* Пояснювати, як реалізуються `if` та цикли;
* Знаходити виклик функції;
* Співвідносити Assembly з відповідними рядками C;
* Переглядати реальні байти машинного коду;
* Пояснювати вплив оптимізації компілятора на створений код.

## 3. Короткі результати кожного експерименту

### Експеримент 1: Підготовка першої програми (`arithmetic.c`)
* **Очікувана логіка CPU для `int result = a + b;`:** Процесор копіює значення змінної `a` (5) зі стеку у внутрішній регістр, значення `b` (7) — в інший регістр. Арифметико-логічний пристрій (ALU) виконує апаратне додавання, після чого результат записується назад у пам'ять для змінної `result`.
* **Аналіз ассемблерного файлу:**
  * Чи кожному рядку C відповідає рівно одна інструкція? **Ні**, один рядок опису логіки на С розгортається у кілька атомарних команд процесора.
  * Чи присутні назви змінних `a`, `b`, `result`? **Ні**, замість них використовуються зміщення відносно базового вказівника кадру стеку, які компилятор MSVC позначає локальними текстовими псевдонімами або прямими зміщеннями через `ebp` (наприклад, `_a$[ebp]`).
  * Тіло функції `main` містить близько **15–20 інструкцій** (через відсутність оптимізації компілятор генерує повний службовий код прологу, епілогу та виклику `printf`).

### Експеримент 2: Знаходження арифметичних операцій (`operations.c`)
При послідовній зміні знаку операції у функції `calculate` зафіксовано заміну відповідних інструкцій в Assembly.

#### Таблиця арифметичних операцій C ➡️ Assembly (MSVC Лістинг):

| Операція в C | Основна Assembly-инструкція (Intel/MSVC syntax) | Опис дії |
| :--- | :--- | :--- |
| `a + b` | `add eax, ecx` або `add eax, edx` | Апаратне додавання значень регістрів |
| `a - b` | `sub eax, ecx` або `sub eax, edx` | Апаратне віднімання |
| `a * b` | `imul eax, ecx` або `imul eax, edx` | Знакове апаратне множення |

**Висновок:** Компілятор змінює лише саму мнемоніку арифметичної команди процесора, тоді як структура підготовки регістрів та робота зі стеком залишаються ідентичними.

### Експеримент 3: Реалізація `if` на машинному рівні (`condition.c`)
Всі файли було **повністю розкоментовано**, відновлено активний код програми, успішно виконано збирання та згенеровано лістинг за допомогою команди `cl /Od /FA /c condition.c`.

#### Фактичний фрагмент отриманого Assembly-коду для функції `_max_value`:
```assembly
_max_value PROC
	push	ebp
	mov	ebp, esp
; Лінія 5: if (a > b)
	mov	eax, DWORD PTR _a$[ebp]
	cmp	eax, DWORD PTR _b$[ebp]
	jle	SHORT $LN2@max_value
; Лінія 6: return a
	mov	eax, DWORD PTR _a$[ebp]
	jmp	SHORT $LN3@max_value
$LN2@max_value:
; Лінія 9: return b
	mov	eax, DWORD PTR _b$[ebp]
$LN3@max_value:
	pop	ebp
	ret	0
_max_value ENDP
```

#### Пояснення, яка інструкція реалізує перевірку `a > b`:
На машинному рівні єдиної інструкції `IF` не існує. Конструкція `if (a > b)` реалізується у два кроки за допомогою комбінації команд порівняння та умовного переходу:
1. **Інструкція `cmp eax, DWORD PTR _b$[ebp]` (Compare):** Процесор порівнює вміст регістра `eax` (куди попередньо завантажили `a`) зі змінною `b` у стеку. Апаратно інструкція виконує віднімання `a - b`. Самі числа не змінюються, але результат віднімання виставляє відповідні прапорці стану (Flags) у регістрі ознак CPU.
2. **Інструкція умовного переходу `jle SHORT $LN2@max_value` (Jump if Less or Equal):** Компілятор діє від зворотного. Оскільки нам потрібно виконати блок при `a > b`, інструкція `jle` перевіряє прапорці стану і, якщо `a` **менше або дорівнює** `b`, процесор здійснює умовний «стрибок» повз блок `if` на мітку гілки `else` (`$LN2@max_value`). Якщо ж умова стрибка не виконалася (тобто `a` дійсно більше за `b`), процесор продовжує лінійне виконання коду і повертає `a`.

### Експеримент 4: Реалізація циклу (`loop.c`)
**Пояснення реалізації циклу:** Поняття `for` в Assembly не існує. Цикл у `loop.asm` реалізується за допомогою лінійного блоку команд, який наприкінці інкрементує регістр лічильника, порівнює його з лімітом за допомогою інструкції `cmp`, а інструкція умовного переходу (наприклад, `jl` або `jle`) повертає виконання процесора назад на початок тіла циклу, створюючи замкнене коло.

### Експеримент 5: Виклик функції (`operations.c`)
* Код функції `calculate` починається з однойменної мітки `_calculate`, а завершується інструкцією `ret 0`.
* Виклик функції у `main` реалізовано за допомогою апаратної інструкції **`call _calculate`**.
* Результат роботи функції перед поверненням записується у регістр **`eax`** (стандарт Calling Convention).

## 4. Приклади реального машинного коду (Завдання 6, 7)
За допомогою утиліти **`dumpbin /disasm:bytes analyze.obj`** на Windows було знято фактичний дамп згенерованого файлу об'єктного коду. Ниче наведено реальні байти та відповідні їм текстові інструкції:

| Address | Machine-code bytes | Assembly | Опис |
| :--- | :--- | :--- | :--- |
| `00000000` | `55` | `push ebp` | Збереження бази стека (пролог функції) |
| `00000005` | `8b 45 08` | `mov eax, dword ptr [ebp+8]` | Перенесення аргументу `start` в `eax` |
| `00000008` | `3b 45 0c` | `cmp eax, dword ptr [ebp+12]` | Порівняння `start` та `limit` (`cmp eax, edx`) |
| `0000001B` | `83 45 fc 02` | `add dword ptr [ebp-4], 2` | Додавання константи 2 до змінної `total` |
| `00000028` | `c3` | `ret 0` | Повернення з функції |

*Фактичні результати `dumpbin` підтверджують, що архітектура x86 є CISC-системою, оскільки інструкції мають різну довжину (від 1 до 4 байт у наведеному фрагменті).*

## 5. Порівняння рівнів оптимізації -O0 та -O2 (`optimize.c`)
* **Прогноз перед експериментом:** Варіант B (Компілятор одразу поверне 30).
* **Результат та порівняння за допомогою MSVC (`/Od` та `/O2`):** 
  При використанні прапорця без оптимізації (`/Od`) компілятор генерував повний виклик функції `answer` та чесно виконував операції додавання. 
  При увімкненні оптимізації (`/O2`) компилятор застосував **Constant Folding** (обчислив `10 + 20 = 30` на етапі компиляції) та **Function Inlining** (повністю видалив виклик `call`, вбудувавши значення `30` безпосередньо у функцію `main`).

## 6. Складнощі під час виконання роботи (Особливості Windows / MSVC)
Під час виконання цієї лабораторної роботи в середовищі **Visual Studio 2022 на Windows** було виявлено та успішно вирішено кілька технічних складнощів, що відрізнялися від стандартної методички для Linux (GCC):

1. **Суть помилки LNK1561:** При спробі виконати пряму компіляцію утиліта `cl` намагається автоматично викликати лінкер (компонувальник) для збирання файлу `.exe`. Лінкер видає критичну помилку `LNK1561: точка входа должна быть определена`, оскільки для успішного зв'язування йому потрібна чітка конфігурація середовища виконання та підсистеми, які не були налаштовані за замовчуванням в x86 Developer Command Prompt.
   * *Рішення:* Було виконано примусове перемикання консолі на 64-бітний режим за допомогою скрипта `vcvars64.bat`.
2. **Призначення параметру `/c`:** Щоб повністю прибрати помилку `LNK1561`, було використано прапорець **`/c`**. Він наказує компилятору `cl` виконувати лише компіляцію сирцевого коду C в об'єктний код (`.obj`) і **повністю відключати етап лінковки**. Створення `.exe` на цьому кроці не відбувається, тому лінкер не шукає точку входу.
3. **Призначення параметру `/FA`:** Використовується замість флага GCC `-S` для нативного середовища Windows. Він наказує компілятору MSVC згенерувати та зберегти на диск текстовий файл із вмістом коду на мові асемблера з розширенням **`.asm`** у зрозумілому для аналізу синтаксисі Intel.
4. **Різниця в інструментах аналізу:** Замість Linux-команди `objdump` використовувалася рідна утиліта Visual Studio — **`dumpbin /disasm:bytes analyze.obj > objdump_output.txt`**, що дозволило успішно отримати байти машинного коду на Windows.

## 7. Додатковий аналіз фінальної програми `analyze.c`
Фінальна програма `analyze.c` поєднує в собі умову, арифметику та цикл всередині функції `process_data`. 

Знятий з неї за допомогою `dumpbin` лістинг демонструє наступні закономірності:
* **Логіка розгалуження умови `if (start < limit)`:** Реалізована через команду `mov eax, dword ptr [ebp+8]` (завантаження `start`), подальшу команду порівняння `cmp eax, dword ptr [ebp+12]` (`limit`) та умовний перехід **`jge`** (Jump if Greater or Equal). Якщо `start` виявився більшим або рівним `limit`, процесор перескакує цикл і йде відразу у гілку `else`, де виконується вичитання `sub eax, 5`.
* **Логіка циклу `for`:** Всередині тіла циклу лічильник `i` ініціалізується нулем у стеку (`mov dword ptr [ebp-8], 0`). На кожній ітерації відбувається безумовний стрибок `jmp` на перевірку умови циклу за допомогою команди `cmp`, яка порівнює `i` з `limit`. Якщо умова істинна, виконується апаратне додавання **`add dword ptr [ebp-4], 2`**, що повністю відповідає С-конструкції `total += 2;`. Після тіла циклу інструкція `add dword ptr [ebp-8], 1` виконує крок `i++`.

## 8. Відповіді на контрольні питання

1. **Що таке ISA?** Instruction Set Architecture — абстрактна модель процесора, яка визначає набір підтримуваних команд, регістри, типи даних та логіку взаємодії з пам'яттю.
2. **Чому CPU не може безпосередньо виконувати C-код?** Бо транзисторні схеми CPU розуміють лише електричні сигнали, закодовані у вигляді бінарного машинного коду (нулів та одиниць).
3. **У чому різниця між Assembly та machine code?** Machine code — це готові для виконання процесором числові байти. Assembly — це той самий код, але записаний у зручному для людини текстовому вигляді за допомогою мнемонік.
4. **Що робить параметр GCC -S (або /FA в MSVC)?** Зупиняє компіляцію після етапу генерації коду ассемблера, зберігаючи його у текстовий файл.
5. **Навіщо ми використовували -O0 (або /Od)?** Щоб вимкнути оптимізацію і отримати максимально буквальний та послідовний переклад рядків C у команди ассемблера.
6. **Що таке operand?** Це об'єкт (аргумент), над яким виконується інструкція (це може бути регістр, адреса пам'яті або число-константа).
7. **Для чого використовується `mov`?** Для копіювання (пересилання) даних між регістрами та пам'яттю.
8. **Яку роль виконує `cmp`?** Порівнює два операнди шляхом віднімання і виставляє відповідні прапорці стану в регістрі RFLAGS.
9. **Як на машинному рівні реалізується `if`?** Через комбінацію команди порівняння `cmp` та інструкції умовного переходу (`jne`, `jg`, `jle` тощо).
10. **Як реалізується цикл?** Зміною лічильника, порівнянням його з лімітом (`cmp`) та стрибком (умовним стрибком) на початок циклу.
11. **Для чого потрібна інструкція `call`?** Для виклику функції із збереженням адреси повернення у стек.
12. **Для чого потрібна `ret`?** Для вилучення адреси повернення зі стека та передачі керування назад у точку виклику.
13. **Чому одному рядку C не обов’язково відповідає одна машинна інструкція?** Оскільки високорівнева операція може містити кілька дій (читання, обчислення, запис), процесор змушений виконувати їх поетапно через свої елементарні інструкції.
14. **Що показує `objdump -d` (або `dumpbin /disasm`)?** Виконує процес дизасемблювання — перетворює бінарні байти машинного коду виконуваного файлу назад у текстові інструкції ассемблера.
15. **Чому Assembly, отриманий з -O0 та -O2, може суттєво відрізнятися?** При `-O2` компілятор перебудовує логіку задля швидкості: видаляє зайві цикли, замінює роботу з пам'яттю на швидкі регістри, заздалегідь рахує константи та видаляє мертвий код.
16. **Чи може компілятор повністю видалити частину написаного програмістом C-коду? За яких умов?** Так, якщо цей код є "мертвим" (Dead code) — його результат ніде далі не використовується, або умова розгалуження ніколи не виконається (наприклад, `if(0)`).
